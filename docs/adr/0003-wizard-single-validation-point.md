# 向导的业务校验单点在 Task intake

架构扫描曾将 `gui/wizard_panel.py`(32KB)列为深化候选:怀疑每步骤重新实现业务校验、绕过后端写裸键。复核后否决——记录于此,避免未来扫描重复提出。

## 事实

- 向导在「完成」时调用 `validate(draft)`(Task intake 导出的唯一业务校验),失败抛 `DraftValidationError` 由对话框展示;每步 `_validate` 只是字段存在性 UI 检查(空输入/路径存在/缓存目录),**不是**业务校验的重复实现(ADR-0001 的单一入口语义成立)。
- `set_setting("wizard_*")` 5 个键是向导 UI 状态持久化(来源/缓存目录/服务器/目标目录/本地路径),无领域后端归属,不属于「绕过 intake」。
- 面板体量来自四步布局与 VersionFetchWorker(列表/版本拉取),是 widget 的自然厚度,不是浅模块。

## 决策

不对 WizardPanel 做深化重构;delete test 判定:删除任何「收敛」都会把校验逻辑移回 GUI 或把 UI 状态塞进领域层,复杂度不集中反而散开。

## 考虑过的方案

- 向导按步调用 validate 片段做提前反馈:是特性工作(更好的 UX),不是深化;面板当前在完成时一次性校验已满足业务正确性——开放为后续需求而非重构。
- 将 5 个 `wizard_*` 设置键收敛为 schema/类型:为纯 UI 状态引类型,Speculative Generality。

## 后果

- 未来架构审查不再把「32KB 向导 / 重复校验 / 裸键写」当作默认候选;向导的消费方身份(ADR-0001)记录在案。
