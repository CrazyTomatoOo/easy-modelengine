# 权重完整性校验策略

下载/传输管线的完整性保障此前是碎片化的:FULL_PIPELINE 有校验阶段,但 DOWNLOAD_ONLY 与 TRANSFER_ONLY 没有;ModelScope 列表元数据里的 Sha256 被丢弃,MS 来源任务在校验阶段全体静默跳过;无源校验和的文件与校验通过的文件不可区分;校验结果不落库,重启即失忆;校验失败后损坏文件留在缓存,而恢复逻辑按大小跳过使坏文件永久滞留;HF 下载器走裸 requests 流式下载(无 SDK 下载校验),同时 HF `get_checksum` 死代码把 git blob(SHA1)当作 sha256 返回。我们决定统一完整性策略:

- **校验覆盖**:所有含下载的任务(DOWNLOAD_ONLY、FULL_PIPELINE)下载后进入校验阶段,按源校验和做全文件哈希比对;校验结果(verify_state、实际哈希)落库并在 GUI 展示。
- **源校验和来源**:平台元数据——HF LFS sha256、ModelScope Sha256;SDK 下载时的内部校验(huggingface 裸流除外、modelscope file_download 实时摘要+重试)保留,与管线校验互补。
- **未校验显式化**:无源校验和的文件(小配置、本地目录)标为「未校验」,不静默通过。
- **校验失败行为**:删除损坏的本地文件后任务 FAILED——否则大小跳过的恢复逻辑会让坏文件永久滞留且被「成功」跳过。
- **远程校验**:传输完成后再对远端副本做 sha256sum 回读比对(rsync/SFTP 皆然);本地源以本地实时哈希为期望值(副本与源一致)。远端校验失败:任务 FAILED,远端残件保留(rsync `--partial` 可续传复用)。平台文件无源校验和(如小配置文件)时,远程校验以传输前的本地实时哈希为期望——校验的是「远端副本与本地一致」,与本地源同语义。

## 考虑过的方案

- **校验仅留在 FULL_PIPELINE**:DOWNLOAD_ONLY 的缓存是用户直接消费的成果物,HF 裸流下载零校验,不校验 = 洞最大处不设防。
- **信任 ModelScope SDK 内部校验、不接线 Sha256**:恢复续传后的旧缓存文件仍无任何覆盖,管线校验阶段对 MS 全程空转,「校验阶段」名存实亡。
- **自动重下失败文件(限次)**:需要引入下载重试机制,超出本题;删除坏文件是任何重试方案的前提,重试机制后续单独设计。
- **远端校验失败删除远端残件**:远端删除是破坏性操作;rsync 残件可被 `--append-verify` 续传复用,删除会丢弃该能力。
- **本地源在本地做哈希校验**:本地即事实源头,自己算自己比是 TOFU 无意义;完整性交给传输侧远程比对。
- **保留 `get_checksum` 接口**:唯一实现返回 git blob_id(SHA1)冒充 sha256,无任何调用者——死代码删除,接口契约一并移除,避免后人误用。

## 后果

- 「通过 / 未校验 / 失败」成为 TaskFile 校验状态的可见契约;「未校验」≠「通过」。
- `verify_state` / `actual_hash` 列首次被写入;GUI 任务详情展示文件级校验状态。
- 传输阶段对每个文件多一次远端回读(SFTP 与 rsync 皆然),大权重远端 I/O 成本接受。
- 域语言新增「源校验和」「远程校验」,TaskFile 校验语义更新(CONTEXT.md)。
